# 内部部署与项目管理数据

本文交付两个部分：内部服务部署配置，以及「项目协同管理｜会议到周报」的数据包和导入工具。所有命令从仓库根目录运行。

## 1. 版本与交付范围

本次提交只包含数据、导入工具及部署配置/文档，不包含本机尚未提交的系统功能代码。**当前远端 `dev` 缺少下列前三项功能文件；完整图表项目部署仍需先合入对应功能代码。本文配置不能消除这个版本依赖。**

部署分支为 `dev`，部署时记录实际提交号，不使用本机未提交工作区作为发布源。

```bash
git clone --branch dev --single-branch https://github.com/noah990127/finflow-studio.git
cd finflow-studio
git rev-parse HEAD
```

必需文件：

- `frontend/src/components/presentations/TaskPresentation.vue`
- `frontend/src/components/WorkResults.vue`
- `backend-java/src/main/java/com/finflow/studio/assistant/PresentationDocument.java`
- `backend-java/src/main/java/com/finflow/studio/assistant/FixedWorkService.java`
- `docker-compose.internal.yml`、`deploy/internal/`
- `examples/project-management/`、`scripts/import-project-management.py`

前三项属于WBS、图表成果展示和图表数据校验功能。若检出的 `dev` 缺少这些文件，说明功能代码尚未合入，不能只靠导入数据实现本文效果。先取得包含这些功能并通过构建的版本，再继续部署。

## 2. 部署拓扑与前置条件

建议Linux x86_64、8核CPU、16GB内存、100GB SSD起步；这是容量建议，不是并发压测承诺。需要Docker Engine、Compose v2、Git、Python 3.11或以上，以及企业HTTPS网关。Python导入工具只使用标准库，无须安装整个Worker环境。

| 服务 | 用途 | 对外入口 |
| --- | --- | --- |
| frontend | 工作台、API与Office同源代理 | 仅绑定宿主机127.0.0.1:5173，由HTTPS网关转发 |
| java-api | 登录、项目、资源、工序与授权 | Docker网络内8080 |
| python-worker | 模型推理、文件处理、PPT生成 | Docker网络内8001 |
| postgres | 元数据、工序与执行记录 | Docker网络内5432 |
| minio | 资料及成果文件 | Docker网络内9000/9001 |
| minio-init | 创建存储桶 | 成功退出0为正常状态 |
| onlyoffice-documentserver | Excel与PPT在线预览 | 工作台 `/office/` 代理 |
| searxng（可选） | 联网搜索 | research配置启用后，仅Docker网络内 |

`docker-compose.internal.yml` 是独立配置，不与根目录 `docker-compose.yml` 合并。默认不开浏览器Agent、外部邮箱或搜索，本项目不需要这些服务。

构建需要访问企业允许的Docker、Maven、npm、Python软件源及Playwright浏览器下载源；模型动态运行需要访问企业模型网关。离线部署见第9节。

ONLYOFFICE当前镜像指定 `linux/amd64`。ARM主机需准备兼容的Office服务或在已验证的模拟环境运行；不能把Mac二进制直接挂进Linux Worker。

## 3. 配置服务

```bash
cp deploy/internal/env.example deploy/internal/.env
chmod 600 deploy/internal/.env
openssl rand -hex 32
```

重复生成独立随机值，填写登录密码、登录签名密钥、数据库密码、对象存储密码、Office JWT密钥和搜索密钥。不要复用示例值。配置文件已被Git和Docker上下文排除。

| 配置 | 要求 |
| --- | --- |
| `FINFLOW_AUTH_DEFAULT_USERNAME/PASSWORD` | 内部管理员登录，不沿用本机默认密码 |
| `FINFLOW_AUTH_JWT_SECRET` | 独立随机会话签名密钥 |
| `FINFLOW_AUTH_SECURE_COOKIE` | HTTPS访问设true；仅SSH本机HTTP验收时暂设false |
| `DATABASE_PASSWORD` | PostgreSQL初次初始化密码；已有卷不能靠改变量直接更换库内密码 |
| `MINIO_ROOT_PASSWORD` | 对象存储凭据，Java与MinIO从同一变量读取 |
| `ONLYOFFICE_JWT_SECRET` | Java与Office必须一致 |
| `AGENT_ENABLED=false` | 默认不开自然语言规划Agent；预置展示和固定模型工序分别说明如下 |

内网Worker Dockerfile显式安装 `.[browser]` 和 `pytz`，以满足Playwright/PPT渲染及Excel处理依赖。它不安装或复制个人Codex/OpenCode登录态。

## 4. 启动与健康检查

为便于后续命令，当前终端定义：

```bash
dc() { docker compose --env-file deploy/internal/.env -f docker-compose.internal.yml "$@"; }
dc config --quiet
dc build
dc up -d
dc ps
dc exec -T java-api curl -fsS http://localhost:8080/actuator/health
dc exec -T python-worker python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:8001/health').status)"
dc exec -T python-worker python -c "import pytz; from playwright.sync_api import sync_playwright; print('render dependencies ready')"
dc exec -T onlyoffice-documentserver curl -fsS http://localhost/healthcheck
```

首次Office启动可能需要数分钟。其余常驻服务应为运行/healthy，`minio-init` 为退出0。`config --quiet` 不打印展开后的密钥；不要将完整 `docker compose config` 输出发到工单或仓库。

在企业HTTPS网关配置内部域名，例如 `https://studio.example.internal`，代理到宿主机 `127.0.0.1:5173`。网关应保留Host、设置 `X-Forwarded-Proto: https`、支持WebSocket，上传限制至少320MB，API/Office长请求超时至少1800秒。部署附带的前端Nginx配置将这些请求转到后端和Office。

短期从个人电脑验收也可使用SSH隧道：

```bash
ssh -L 5173:127.0.0.1:5173 deploy-user@server
```

这种HTTP方式需要暂将服务器 `FINFLOW_AUTH_SECURE_COOKIE=false` 并重建Java服务。正式HTTPS域名上线后改回true，运行 `dc up -d java-api`。不要为方便而把数据库、MinIO控制台或Java API额外暴露到公网。

## 5. 导入项目资料与可视化工序

### 5.1 校验数据包

```bash
python3 scripts/import-project-management.py --validate-only
```

脚本校验全部文件的SHA-256、工序资源绑定、17项唯一叶子任务以及工时汇总。无须连接服务。

### 5.2 导入预置成果

```bash
python3 scripts/import-project-management.py \
  --base-url https://studio.example.internal/api \
  --username admin
```

终端会提示输入工作台登录密码。若通过SSH隧道导入，将地址改成 `http://127.0.0.1:5173/api`；其他远程HTTP地址会被导入器拒绝，避免明文传输登录凭据。

脚本会：

1. 登录目标工作台，创建「项目协同管理｜会议到周报」。
2. 上传Excel、会议口述稿、同源JSON、模板和已备成果，所有资源在目标环境生成新ID。
3. 创建「项目进展看板」及三个业务步骤。
4. 通过真实 `presentation.render` / `document.render` 工序重新渲染视图和PPT，并等待成功。

这一步不用模型密钥、不调用Agent CLI；也不会把旧执行日志导入后伪装成新环境的模型执行。数据包包含原PPT供对照，新看板中的PPT由目标Worker重新生成，因此可以验证渲染依赖。

导入状态保存在 `.run/project-management-import.json`，包含目标地址、账号名、资源ID和执行ID，不含密码或模型密钥。备份这个文件；同一环境重新运行同一命令会继续未完成步骤，已成功部分不会重复执行。

异常处理：

- 已有同名项目但缺失状态文件：脚本停止，先找回状态文件；确需建立第二份时同时指定 `--project-name 新名称 --state .run/另一个状态.json`。
- 等待超时：服务可能仍在运行。重新执行同一命令观察，不能随意换状态文件重复提交。
- 已明确失败：先排查服务日志，再加 `--retry-failed`。默认不自动重试失败工序。
- 数据包更新：使用新项目名、新状态文件验证，不把旧状态强行用于不同数据包。

## 6. 启用可重新分析的完整工序

预置看板适合部署验收。处理新会议稿、新台账则需要完整分析工序和模型API。

### 6.1 配置模型

Worker默认API路径使用 `FINFLOW_LLM_PROVIDER=codex`，该适配器需要兼容Responses接口的网关。填写：

```dotenv
OPENAI_BASE_URL=https://approved-model-gateway.internal/v1
OPENAI_API_KEY=服务器私有密钥
OPENAI_MODEL=企业批准的模型名
OPENAI_MAX_OUTPUT_TOKENS=16000
```

然后运行 `dc up -d python-worker`。输出长度不足可能造成JSON被截断，不要将缺失字段或错误结果手动标记成功。

若企业网关只有Chat Completions接口，可由导入器给完整工序配置自定义模型。密钥仅发到目标服务，由后端加密保存：

```bash
export FINFLOW_IMPORT_MODEL_BASE_URL=https://approved-chat-gateway.internal/v1
export FINFLOW_IMPORT_MODEL=企业批准的模型名
read -r -s -p '模型API密钥: ' FINFLOW_IMPORT_MODEL_API_KEY
export FINFLOW_IMPORT_MODEL_API_KEY
```

不要在Shell历史中直接写密钥。导入结束后 `unset FINFLOW_IMPORT_MODEL_API_KEY`。

### 6.2 发布和执行

```bash
# 仅发布完整分析工序，不调用模型
python3 scripts/import-project-management.py \
  --base-url https://studio.example.internal/api --username admin --include-live

# 显式执行完整工序；会调用模型并生成新版本成果
python3 scripts/import-project-management.py \
  --base-url https://studio.example.internal/api --username admin --run-live
```

完整工序名称为「周会任务更新与风险汇报」。它从会议稿和台账读取输入，重建WBS、人员视图、热力图、风险报告及PPT。固定工序按发布时模型配置执行；改模型后需要重新发布实现版本，不能把旧模型校验记录当作新模型执行结果。

当前数据链路使用Excel逐单元格导出的同源JSON。会前/会后Excel保留为底稿和快照；本次并未实现Excel自动双向同步。修改输入时，会议稿和对应JSON都要更新，不能只上传新Excel就认为工序输入已同步。

### 6.3 自然语言Agent建工序（可选）

点击已发布工序「执行」不需要规划CLI；让Agent接受自然语言并新建/修改工序，则需要额外准备企业批准的OpenCode CLI。

`deploy/internal/Dockerfile.worker` **不自带OpenCode CLI**。部署团队须在派生Worker镜像安装经批准的Linux版本及其运行依赖，或使用预装运行时的内部镜像；将提供方配置只读挂载到容器中。不能仅设置环境变量便认为CLI已经安装。

设置 `AGENT_ENABLED=true`、`AGENT_RUNTIME=opencode`、容器内的 `OPENCODE_CLI_PATH`、`OPENCODE_MODEL=提供方/模型` 和 `OPENCODE_PROVIDER_CONFIG=容器内配置路径`。这些配置由Compose透传。先在Worker中验证CLI `--version` 和模型认证，再在新会话中发起无外部提交的简单任务。

如需联网检索，再运行 `dc --profile research up -d`。浏览器Agent、邮箱登录及发送不在本项目数据包部署范围内，不能复制开发者浏览器资料来启用。

## 7. 页面验收

1. 登录，进入「项目协同管理｜会议到周报」→「项目进展看板」。
2. 展开工作进展，三个步骤应执行完成。
3. 第2步，在成果下拉框中切换项目WBS、人员分工、人员繁忙程度热力图。热力图应直接显示彩色色块，不能只看到文件名或普通文本。
4. WBS包含17项叶子任务，人员视图包含相同任务。顶部计数可能含分组行，不能拿该计数代替叶子任务数。
5. 热力图按负载降序：王磊183.3%、陈宇162.5%、林悦112.5%；共3人超负荷，正缺口44小时，总负载176/184小时。统计周期固定为11月30日至12月4日，不是实时在线监测。
6. 第3步打开6页PPT，中文可读，下载后文件能打开；风险、待决策和已确认事实区分清楚。
7. 再运行同一导入命令，应复用原项目/资源/成功运行，不生成第二套数据。

动态工序会重新调用模型，必须重新核对计算和视图；预置数据通过并不保证任何后续模型输出都正确。

## 8. 日志与常见问题

```bash
dc logs --tail=150 java-api python-worker
dc logs --tail=100 onlyoffice-documentserver
dc ps
```

| 现象 | 检查 |
| --- | --- |
| 登录后401或跳回登录 | 登录密码、HTTPS与Secure Cookie设置；网关是否保留Cookie |
| 导入404、实现定义校验失败 | 服务版本是否包含通用图表展示/固定工具工序功能；不要直接导数据库绕过API |
| Excel读取报pytz或PPT缺Playwright | 是否用了内部专用Worker Dockerfile，是否重新构建并替换了旧容器 |
| 热力图有文字但无色块 | 导入的是最新内联样式数据包；预览会过滤style标签和脚本 |
| Worker健康但Agent不可用 | 健康检查不证明CLI/模型已认证；按6.3单独验证 |
| 模型JSON截断或模型配置变化 | 检查上下文与输出上限、配置快照，失败后不自动覆盖有效成果 |
| Office空白或无法下载 | `/office/`代理、JWT一致性、Document Server到java-api:8080连通性、HTTPS转发头 |
| 图片/文件404 | MinIO桶、对象卷是否与PostgreSQL及API密钥卷来自同一套备份 |
| 修改.env后未生效 | 用 `dc up -d 对应服务` 重建容器；`restart`不会重新加载容器环境变量 |

日志可能包含业务资料，按内部制度保留；不要将含密钥、人员真实信息或登录Cookie的日志推到Git。

## 9. 离线部署

在可联网、与目标服务器CPU架构一致的构建机上完成 `dc build` 和 `dc pull --ignore-buildable`。记录Git提交号和镜像ID，通过内部镜像仓库交付，或使用 `docker save`/`docker load` 转移**所有**业务与依赖镜像。

业务镜像名称是 `finflow-internal/frontend:local`、`finflow-internal/java-api:local`、`finflow-internal/python-worker:local`；依赖镜像以 `docker-compose.internal.yml` 为准，包括PostgreSQL、MinIO及mc、ONLYOFFICE；启用搜索时还需SearxNG。可设置 `FINFLOW_IMAGE_TAG` 固定企业发布标签，不能混用不同架构镜像。

目标机同时接收相同提交的仓库文件（含Compose、部署Nginx配置和数据包），自行填写私有 `.env`。镜像已导入后：

```bash
dc up -d --no-build --pull never
```

模型服务必须能在内网访问。预置看板导入无模型依赖；动态分析仍需模型API。浏览器二进制、中文字体和LibreOffice已装入Worker镜像，不能留到离线运行时再下载。

## 10. 持久化、升级与回滚

必须成套保留PostgreSQL数据、MinIO对象、`api-data`卷以及服务器私有配置。`api-data`内含模型凭据加密密钥、数据连接密钥和缓存；仅备份数据库会导致文件或密钥缺失。

先停止接收新任务，等待运行结束，再停应用写入服务：

```bash
dc stop frontend java-api python-worker
mkdir -p backups
chmod 700 backups
dc exec -T postgres pg_dump -U finflow -d finflow -Fc > backups/finflow.dump
```

随后由部署平台对对象存储卷、API数据卷和Office数据卷做同一停写窗口的快照/备份；停止存储服务后再做文件系统级归档，不能复制正在写入的数据库目录。私有配置与密钥备份进入企业密钥存储，不进入代码仓。备份结束用 `dc up -d` 恢复应用。

升级前记录当前Git提交号、镜像标签和备份编号；新版本先在独立环境导入本数据包验证。回滚使用旧镜像及兼容的整套数据备份，不能假设数据库结构可以自动降级。不要运行 `docker compose down -v`，它会删除持久卷。

## 11. 本次验证范围

提交前检查包括数据包SHA-256与工时一致性、导入脚本在独立项目的真实API导入、工序实际渲染、重复导入行为以及WBS/热力图页面切换。容器构建、目标服务器网络、企业模型、HTTPS域名和Office网关必须以部署现场验收为准；健康检查不能替代这些检查。
